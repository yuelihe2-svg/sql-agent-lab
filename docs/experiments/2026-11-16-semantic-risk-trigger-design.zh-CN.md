|---|---:|---:|---|

| 空结果 | 0 | 4 | 当前样本没有合法空结果正例，不能据此把空结果当错误 |

24 道正确题的已保存完整类型扫描均未记录 NULL；因此本批也不足以评估“正确 NULL 被误修”的风险。需要单独设计反例。现有内连接提示还遗漏了活动预算重复累加案例，说明只匹配 SQL 关键词远远不够。

人工分析使用参考答案帮助定位差异；**未来运行时的触发器只允许读取用户问题、用户提供的补充说明、可信 schema/字段说明、候选 SQL 与只读探查证据**。题号、参考 SQL、评分结果和这些人工标签均不能进入 Agent 上下文或运行时规则。

“参考结果不一致”是本实验的正确率口径，不是对所有业务解释的绝对裁决。字段含义有歧义时应保留不确定性。以下归类每题选一个主要问题用于汇总，不代表每题只有一个问题，也不代表新触发器能识别全部问题。

## 3. 触发协议：不要把“可疑”直接变成“重写”

保留现有执行失败/类型不匹配修复路径。对执行成功的 SQL，另行形成语义风险报告，未来可选地接入以下分级流程：

1. **`no_signal`**：没有已支持的风险信号，正常返回；不能显示“语义正确已验证”。
2. **`needs_probe`**：存在结构或格式疑点，但缺少数据证据；先做有预算的只读探查，不调用 Refiner。
3. **`needs_review`**：存在可引用的需求/元数据依据，且 SQL 结构或探查结果显示具体冲突；建议交给 Refiner 复核，允许其回答证据不足。
4. **`needs_clarification`**：关键业务映射缺失或有多种合理解释；说明歧义，请用户或数据源维护者确认。不能猜测字段或编码后自动修复。

解析失败、超时、截断、未知函数或不支持的 SQL 结构单独记为 `assessment=incomplete`；不能归为无风险。风险决定和检查完整度是不同字段。

每条 finding 建议至少保存：`rule_id`、需求原文及来源、涉及 SQL 片段、可信元数据引用、探查结果及完整度、触发/抑制理由、待确认假设和建议下一步。不生成没有校准依据的“置信度 0.95”。

业务约定包含：统计总体、计数/求和单位、分组层次、时间口径、允许的缺失值、输出单位和并列规则。第一版只接受显式约定或可核验映射；未知字段保持未知，不能根据几个关键词就宣布已经理解整道题。将来自然语言提取也可能出错，需要保留原文和不确定项。

### T1：聚合单位与连接放大

- 低成本信号：`SUM/AVG/COUNT` 的输入跨越一对多关系；多个子表同时连接同一实体；按实体计数但使用关系行键。
- 升级证据：已知“每条预算/每个地区/每笔交易计一次”的约定；聚合输入中，同一贡献实体的主键出现多次；确认没有正确的预聚合或实体去重。
- 只读探查：在原过滤范围内比较贡献主键计数与不同主键计数，或寻找一个贡献主键重复出现的实例。复合主键使用列组，不能拼接字符串模拟唯一键。找不到可靠键、窗口函数或复杂作用域不支持时返回不确定。
- 抑制条件：用户本来要求按交易频次加权、按关系计数；已按正确单位预聚合；连接目标唯一；重复行不进入被检查的聚合。
- 禁止通用修复：不能见 JOIN 就补 DISTINCT，尤其不能把 `SUM(amount)` 改成 `SUM(DISTINCT amount)`。两条不同预算可能金额相同。

### T2：总体遗漏与零参与实体

- 低成本信号：明确要求全部符合条件的实体，而查询从事件明细出发，或 INNER JOIN/右表 WHERE 条件可能排除零关联实体。
- 升级证据：从实体表及其自身资格条件构造出的总体，存在被查询排除的实体；排除理由只有可选关系不存在，且问题要求保留它们。
- 抑制条件：用户明确要求“参加过”“有检测记录”“至少一次”；总体本身就以存在某关系定义。不能仅看到“每个”就改 LEFT JOIN。
- 注意：零参与者与存在记录但测量未知是两种情况。计数零通常有明确意义，缺失测量不能随意补零。合格赛事条件仍应保留，不能为了保留车手而把赛事资格条件删掉。

### T3：格式、有效值、缺失编码

- 低成本信号：明确数值/时长要求却按文本比较；标识符匹配为空且存在格式差异；列表要求完整成员但使用子串；转换后发生 NULL 或不合理的默认零。
- 升级证据：可信字典定义时长格式、列表分隔规则、合法数值语法、缺失编码或标识符规范；探查发现当前谓词漏掉/纳入不符合该定义的具体输入。
- 抑制条件：格式有序且已规范化的文本；合法负数/零；用户明确匹配子串；标识符的前导零有意义。没有字典时只能报告疑点，不得从样本推断“0 一定是未知”。
- 标识符规范化还必须检查碰撞。即使去前导零能找到一条记录，也不自动证明该映射符合用户意图；禁止全库一律 CAST 编号。
- `GLOB '[0-9]*'` 不是完整数字语法。未来需要按明确领域规范校验，不能用排除负数来换取“看起来是数字”。

### T4：层次、时间、枚举与输出约定

- “每个实体至少若干项”应检查阈值所在分组层次；“每位车手最佳圈后再排名”应检查先聚合再排名。没有可靠的实体映射，只保留疑点。
- “截至某日有效”与“恰好某日发生”不同；必须知道历史记录的生效含义，不能一律把等号改成小于等于加取最大日期。
- “阳性”“已记录”“服务年级”等业务词须有明确映射；不能凭列名或几个取值样本推断医学编码或业务含义。
- 明确的一行文本、输出列数、单位、并列规则可形成较强的契约检查；普通表达不能被随意解释为严格格式要求。
- 这些问题先列入设计和案例库，不作为第一批全部实现的承诺。

## 4. 空结果和 NULL 的保护规则

**空/NULL/零本身都不是语义错误，不单独触发模型修复。**

| 观察 | 合法含义 | 默认动作 | 何时进一步取证 |
|---|---|---|---|
| 查询返回 0 行 | 没有满足条件的记录 | 如实说明没有匹配记录，保留 SQL | 有独立格式/字段冲突证据，不因问题措辞期待结果就假设一定存在 |
| 非分组 COUNT 返回 0 | 条件内确实没有对象 | 正常返回 0 | 总体或过滤范围存在独立风险 |
| AVG/SUM 返回 NULL | 没有非空输入等情况 | 说明暂无可计算值，不冒充 0 | 需要区分空总体、全部未知或转换问题时作诊断 |
| LEFT JOIN 可选字段 NULL | 没有关联资料，或关联字段未知 | 保留未知含义 | 查询本应保留的主体也被过滤掉 |
| 指标中有 0 或负数 | 可能是合法观测 | 不按通用正数规则删除 | 可信领域字典明确定义其为缺失/非法 |
| COALESCE(...,0) | 用户明确要求无事件计零 | 保留明确约定 | 转换错误或未知测量被掩盖成零，违反已有约定 |

SQLite 的 `COUNT(*)`、`COUNT(column)`、`AVG` 和 `SUM` 对空输入/NULL 的行为不同；其中 AVG 没有非 NULL 输入时返回 NULL，SUM 也可能返回 NULL。[SQLite 聚合函数文档](https://www.sqlite.org/lang_aggfunc.html)

必要时并列探查同一范围的行数、目标字段非空数和有效转换数。这些计数用来解释差异，不自动重新定义“有效”。分组查询还要保留分组范围；不能把无 GROUP BY 的 COUNT 行为直接套到每组或零行查询。

例如：输入原本有字符串，但日期转换全部失败，需要检查格式；输入原本全是未知日期，NULL 可能完全正确。二者都不能通过“补 0 直到非空”修复。

探查建议沿用最多 3 次、累计最多 2 秒的只读预算，并增加扫描/输出约束及同一数据快照要求。当前 `sql_diagnostics.py` 仅实现 `NOT IN` 右侧 NULL 探查，这些新探查还没有实现。探查超时或只查了样本时，未找到反例不等于完整验证；看到一个真实反例可以证明局部风险，但不自动证明整题答案错误。

## 5. Refiner 以后接收什么，什么情况下采用修改

未来候选输入：原问题、已确认的业务约定、相关 schema、原 SQL、原执行反馈，以及上述带来源的 finding。Refiner 先说明冲突是否成立；返回 `keep`、`propose_revision` 或 `inconclusive`。不能要求它“必须修好一个错误”。

第一阶段仅输出建议，不覆盖原结果。若后续开放自动采用，仍须执行候选并检查：原有条件、总体、输出列、计数单位、单位和 NULL 约定是否保留；原风险的证据是否消除；是否新增无依据条件。候选能执行、结果非空、与原答案不同都不足以证明修改更正确。现有执行/列数回退保护不足以独立批准语义修改，需另行设计验收。

任务 `completed` 仅表示处理完成。语义复核状态独立展示为未检查、有疑点或无法确认；不要把“模型说通过”显示成“答案保证正确”。本次不修改页面和任务状态机。

## 6. 实现顺序与无模型验收

建议先做 **T1 连接导致聚合重复贡献**，只产出结构化风险报告，不接模型、不改 SQL。它在本批对应多个错误，有较明确的记录键证据，也容易构造反例。然后再做 T2；T3/T4 逐项依据字段元数据扩展。

拟议修改范围：独立实验模块与离线测试、风险报告数据结构。初期不修改 `reference_baseline.py` 的路由，不修改提示词、不切换现有实验性 semantic review、不动默认应用与 main。后续集成另作独立变更，便于判断收益来源。

验收必须同时包含正确与错误 SQL：

1. 本批 26 错题用于开发诊断，24 正确题用于发现误触发；这 50 题都已被查看，不再充当独立测试集。
2. 构造合法空结果、COUNT 零、空集合 AVG NULL、全未知 AVG NULL、可选关系 NULL、明确 COALESCE 零、合法负数、正确 INNER JOIN 等反例。
3. 聚合测试覆盖重复贡献、相同金额的不同预算、正确预聚合、唯一连接、用户明确要求加权、复合键、无主键和分析超时。
4. 记录风险是否找对原因、错题漏报、正确题误报及分析不确定比例。不能只统计“提醒过多少错题”，也不能把结构疑点视为已诊断根因。
5. 规则冻结后，再使用未参与设计的问题/数据库验证泛化。将来授权模型实验时，固定同一初始 SQL，比较不复核、风险触发复核、全量复核；单列修好、改坏、未变、无法确认、模型成本和探查成本。

本次实际执行了保存 trace 的离线统计，以及 11 个内存 SQLite 反例/示例检查，全部符合预期。其中同一活动两条各 10 的预算连接两条出席记录后，普通 SUM 得到 40，SUM(DISTINCT amount) 得到 10，而正确的预算合计是 20，说明去重金额不是通用修复。

**这 11 项仅验证 SQL 行为与设计反例，没有验证尚未实现的新触发器，更没有证明模型准确率提高。** 未重跑真实题目 SQL、未调用模型、未改共享数据库。原有 Agent 源码和默认运行行为保持不变。
