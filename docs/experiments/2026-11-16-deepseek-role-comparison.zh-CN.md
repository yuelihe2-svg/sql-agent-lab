# SQL Agent Lab 单角色与三角色实验总结

本次 50 题配对实验没有观察到当前三角色配置提高严格执行结果匹配率：单次生成 A、可修复单角色 B 均为 25/50，条件式三角色 C 为 24/50。差距只有一题，不能据此断言三角色普遍更差。

Trace 显示，C 的 Selector 确实压缩了生成阶段的上下文，但没有带来净准确率收益；Decomposer 完成了 SQL 生成，但没有独立验证拆解步骤；Refiner 在本批真实运行中没有触发，不能评价其纠错效果。当前系统具有可观察、可限制、只读执行的工程价值，而这套角色分工的准确率优势尚未得到证明。

本文仅保留汇总指标、方法、代码入口与抽象化错误分析，不包含题目原文、预测或参考 SQL、数据库内容、模型回复、逐题表或原始日志。

## 实验设置

实验日期为 2026 年 11 月 16 日。代码基于 `main` 的 `ffff15b`，在独立实验分支运行；真实执行版本为 `3da66ed`。C 直接使用原有 `ReferenceMacSQLAgent`，未修改生产工作流、提示词或路由。

| 配置 | SQL 生成与修复 | 模型调用上限 | 修复次数上限 |
| --- | --- | ---: | ---: |
| A | 通用提示词生成一次，执行后结束 | 1 | 0 |
| B | 与 A 完全相同的首次提示词，同一角色接收执行或类型反馈后修复 | 3 | 2 |
| C | 条件式 Selector、Decomposer、Refiner | 3 | 1 |

所有配置使用 `deepseek-flash`，API 返回标识也是 `deepseek-flash`；执行时官方文档将其标注为 DeepSeek-V4.1-Flash-1017。设置 temperature=0、thinking 关闭，每题每组运行一次，无自动重试。三组复用数据库快照、字段说明、检索、值查询、只读执行、类型检查及独立评分器，关闭实验语义复核。

每任务 token 预算为 50,000，输入采用 14,000 UTF-8 字节的保守预算；生成输出按既有规则上限为 1,000 或 2,400 token。B、C 共享既有修复采纳保护，被拒绝或未变化的修复会提前结束。调用上限不代表每题实际调用次数相同。

样本从本机固定 BIRD mini-dev 题库按数据库和原始难度标签比例分层抽取，种子为 20261116，排除 21 个已知回归或试点题号。50 题覆盖 11 个数据库，包含 47 道 challenging、2 道 moderate、1 道 simple。未全面核查其他历史实验是否使用过这些题，因此定位为探索性实验。最多同时运行三道题，每题内轮换 ABC、BCA、CAB 的配置顺序。

## 结果与开销

主要指标比较预测 SQL 与参考 SQL 的完整结果集合，忽略行顺序和重复行，但保留列顺序。参考答案只进入后置独立评测器。这是本项目的评分口径，不等于所有业务语义都正确，也不直接对应官方榜单成绩。

| 指标 | A 单次生成 | B 单角色可修复 | C 条件式三角色 |
| --- | ---: | ---: | ---: |
| 完成题数 | 50 | 50 | 50 |
| 匹配参考结果 | 25 | 25 | 24 |
| 严格结果匹配率 | 50% | 50% | 48% |
| SQL 可执行 | 50 | 50 | 50 |
| 实际模型请求 | 50 | 50 | 61 |
| 输入 token | 109,163 | 109,163 | 124,482 |
| 输出 token | 5,994 | 5,874 | 7,032 |
| 平均 Agent 耗时 秒 | 2.27 | 2.41 | 2.39 |
| 中位 Agent 耗时 秒 | 1.89 | 1.83 | 2.06 |
| 峰值无缓存费用估算 美元 | 0.03994 | 0.03980 | 0.04578 |

共 161 次真实 API 请求、361,708 token，费用估算合计约 0.12552 美元。估算采用执行时[官方价格](https://api-docs.deepseek.com/quick_start/pricing/)中的输入 $0.30/M、输出 $1.20/M，不是实际账单；缓存和非峰时段可降低费用。Agent 耗时包括输入准备、工具和模型处理，不包括后置参考评测；网络、缓存与并发负载会影响时间。

C 相对 B 有 2 题胜出、3 题落后、22 题共同正确、23 题共同错误，净差为 −2 个百分点。按数据库整组重采样 10,000 次的探索性 95% 区间约为 [−11.8, +7.9] 个百分点；仅有 11 个数据库簇，不能作强推广。

A、B 的 50 份首次请求消息逐题完全一致，实际均只调用一次模型；33 题的 SQL 原始字符串不同，其中 6 题的评分不同，双方各赢 3 题。因此 A/B 的本次差异不是修复造成的，字符串不同也不都意味着语义不同。temperature=0 没有使独立请求完全确定。

## Trace 核查范围

逐题检查了全部 150 份 trace、任务结果和 API 记账：开始、完成及付费请求记录数量一致，token 汇总一致，161 个响应 ID 均非空且互不重复。三组每题读取的完整 schema 和检索结果一致。没有请求失败或评测未决，批次结束后 11 个共享数据库的哈希均与运行前一致。

| 观察项 | A | B | C |
| --- | ---: | ---: | ---: |
| 模型 Selector 调用 | 0 | 0 | 11 |
| SQL 生成调用 | 50 | 50 | 50 |
| 模型修复调用 | 0 | 0 | 0 |
| 类型检查 ok | 33 | 31 | 33 |
| 类型检查 unverified | 16 | 19 | 17 |
| 类型检查 mismatch | 1 | 0 | 0 |

`unverified` 表示没有充分确认类型契约，不能写成“检查通过”。A 的一题出现类型不匹配，但 A 按定义禁止修复；B、C 的输出没有出现修复触发条件。没有语义复核请求。

## Selector 有上下文压缩作用但未证明准确率收益

Selector 在 C 的 11 题中实际运行，全部生成可用的筛选结果，没有 fallback。这 11 题中 A、B、C 各答对 5 题；C 相对 B 一胜一负，其余相同。

| 这 11 题的输入开销 | A 或 B | C |
| --- | ---: | ---: |
| SQL 生成阶段输入 token 合计 | 28,263 | 11,563 |
| Selector 输入 token 合计 | 0 | 26,921 |
| 全任务输入 token 合计 | 28,263 | 38,484 |

下游 SQL 生成输入减少约 59.1%，但加上 Selector 自身后，总输入增加约 36.2%。所以本批可以证明它压缩了生成输入，不能证明它降低了总开销。

匿名失败案例中，题目需要覆盖全部实体，Selector 只保留了发生过事件的明细表，丢掉保存完整实体总体的表。后续 SQL 对明细中的实体求平均，遗漏没有事件的实体，结果与参考不匹配。筛选遗漏与后续错误方向一致，但仍需固定生成提示词的消融实验才能量化筛选的独立影响。

此外，当前触发条件检查的是未压缩的完整提示词长度。仅用已保存 trace 做无模型检查发现：这 11 题都可以通过现有 `_fit` 的 level 1 压缩，在相同预算内保留完整表列标识符。A/B 的真实运行也都采用该压缩级别。因此本批的模型 Selector 并不是“完整标识符一定放不下”时的唯一办法。这个检查没有重新调用模型，也不能预测跳过 Selector 后会生成什么答案。

实现依据：[筛选、触发条件与压缩](../../src/sql_agent_lab/macsql/reference_baseline.py)。

## Decomposer 完成生成但不是逐步执行的分解器

C 的 50 次生成回复中，30 次直接输出 SQL，13 次在 SQL 前给出列表式计划，7 次给出简短文字概述。这些文本和最终 SQL 来自同一次模型回复。

代码取最后一个 SQL 代码块作为答案，状态中的 `plan` 仍为空列表；没有把计划拆成独立节点逐个执行，也没有逐步检查每个子问题的输出。因此可以确认 Decomposer 在生成 SQL，却不能把它描述为已实现逐步执行与验证的分解系统。

未调用 Selector 的 39 题中，A、B 各答对 20 题，C 答对 19 题；这部分主要比较不同生成提示词与独立生成波动。C 的某些错误给统计范围额外增加了限制，另一些题则与 A/B 一样在多表关联后重复累计。执行成功不会暴露这些语义错误。

目前没有证据证明简短计划本身提高了准确率。应固定相同 schema、模型和输出预算，只比较通用生成提示词与计划提示词，才能更清楚地回答这一点。

实现依据：[生成、SQL 提取与 plan 状态](../../src/sql_agent_lab/macsql/reference_baseline.py)。

## Refiner 本批没有被检验

B、C 都没有执行错误或类型 `mismatch`，所以按既有路由正常结束，没有调用 Refiner。这符合当前设计，不是节点调度故障，也不能说明 Refiner 永远无用。

修复触发条件是执行失败或输出类型不匹配。空结果、NULL、类型未确认以及结构风险提示不会自动触发修复；例如关联计数风险仅是建议。语义复核关闭时，统计总体、分母、重复累计和输出列契约等错误可能一直保留。

先前“SQL 都能执行”不等于“类型全部通过”：A 有 1 题类型不匹配，三组也各有类型未确认的结果。已有离线测试证明部分修复、停止和采纳保护分支可以工作，但不能替代真实模型纠错收益的测量。

实现依据：[修复路由](../../src/sql_agent_lab/macsql/reference_baseline.py)、[类型检查](../../src/sql_agent_lab/macsql/reference_core.py)、[只提示而不自动改写的风险检查](../../src/sql_agent_lab/macsql/result_risks.py)。

## 评分差异需要与业务错误区分

一个 B 的失败案例返回了与参考相同的全部信息，但把排名列放在最后。事后只读核对确认，将该列移到第一列后，完整结果集合一致。主表仍保留预先约定的严格评分，没有事后改分；该失败应归类为列顺序契约差异，而不是统计值全部错误。

其他匿名案例涉及真正的业务口径差异：额外缩小统计总体、丢掉零事件实体、多表关联放大累计值。未来错误分析应分开统计这些类别，避免把所有不匹配都称为同一种语义错误。

## 后续实验建议

1. **先检验 Selector 的必要性。** 固定 C 的生成提示词与预算，对比“完整 schema 的现有压缩”与“模型筛选”；重点检查完整实体总体、零事件实体和连接路径是否保留。
2. **单独检验分解提示词。** 固定 schema，只切换通用生成与简短计划提示词，增加独立重复，避免把一次生成波动归因于角色命名。
3. **给修复机制相同的起点。** 在独立诊断集中，向通用修复与 Refiner 提供完全相同的初始 SQL 和执行反馈，报告修复成功率、未修好比例、误改率与额外开销。诊断集不能替代普通题目的端到端准确率。
4. **另测语义检查。** 若目标是发现“能执行却答错”，应把语义检查作为独立变量，测量净收益、误改和费用；不在这批已看过的题目上改提示词后宣称泛化提升。

本次分析不改 Agent 工作流，不触发新的模型请求。下一次确认性评估应使用新的题目集合。工程上的只读边界、工具封装和可观察性仍值得保留；是否保留额外模型角色，应由受控实验中的准确率与开销决定。
