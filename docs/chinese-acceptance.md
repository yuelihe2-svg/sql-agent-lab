### 明确修改筛选条件（离线验证）

工作区会从同一对话、同一数据源最近一轮公开结果的完整 SQL 提取条件。
支持 `改成2023年`、`城市改成杭州`、`状态改成paid`；只替换已有的
`year`、`city`、`status` 等值筛选条件，保留指标、其他筛选、分组、排序和数量限制。
这些字段名是当前支持边界，不会自动推断其他数据库中的同义字段或翻译状态值。

例如先问“统计2024年上海已付款订单总金额”，随后问“城市改成杭州”，再问
“改成2023年”。预期后两次分别保留2024年/已付款、杭州/已付款条件。
具体数值应以测试数据库的只读参考查询为准。

“改成杭州”没有明确修改字段时会先澄清；明确修改遇到复杂关联、OR、区间条件、
缺少目标字段、失败或截断的最近查询也会要求补充条件，不能跳过最近一轮去套用更早 SQL。
自然表达“那杭州呢？”保留现有模型理解流程，本轮不宣称已获得确定性保障。
新对话和切换数据源后直接问“城市改成杭州”应澄清，不继承其他对话的条件。

派生条件与历史共用 1600 字节预算，并继续受最终 ContextPolicy 限制。工作区在发布
结果前检查最终 SQL 的结构。如果模型漏掉条件或改动了查询口径，系统使用从上一轮
推导出的 SQL，经只读预检和执行后返回新结果。修复无法执行时会请用户重述条件。
检查采用保守的结构比较，等价但写法不同的 SQL 也可能走修复路径。它验证的是
明确修改是否保留上一轮口径，上一轮口径本身仍需核对。
