### 明确修改筛选条件（离线验证）

工作区会从同一对话、同一数据源最近一轮公开结果的完整 SQL 提取条件。
支持 `改成2023年`、`城市改成杭州`、`状态改成paid`；只替换已有的
`year`、`city`、`status` 等值筛选条件，保留指标、其他筛选、分组、排序和数量限制。
这些字段名是当前支持边界，不会自动推断其他数据库中的同义字段或翻译状态值。

例如先问“统计2024年上海已付款订单总金额”，随后问“城市改成杭州”，再问
“改成2023年”。预期后两次分别保留2024年/已付款、杭州/已付款条件。
具体数值应以测试数据库的只读参考查询为准。

“改成杭州”没有明确修改字段时会先澄清；明确修改遇到复杂关联、OR、区间条件、
缺少目标字段、失败或截断的最近查询也会要求补充条件，不能跳过最近一轮去套用更早 SQL。
自然表达“那杭州呢？”保留现有模型理解流程，本轮不宣称已获得确定性保障。
新对话和切换数据源后直接问“城市改成杭州”应澄清，不继承其他对话的条件。

派生条件与历史共用 1600 字节预算，并继续受最终 ContextPolicy 限制。工作区在发布
结果前检查最终 SQL 的结构。如果模型漏掉条件或改动了查询口径，系统使用从上一轮
推导出的 SQL，经只读预检和执行后返回新结果。修复无法执行时会请用户重述条件。
检查采用保守的结构比较，等价但写法不同的 SQL 也可能走修复路径。它验证的是
明确修改是否保留上一轮口径，上一轮口径本身仍需核对。

### 首轮统计口径

- “看看去年销售情况”先询问要看销售总金额、订单数量还是按月趋势。
- “统计2024年已付款订单总金额。已付款指 status = paid。”在有 `orders(year, status, amount)` 的数据源检查年份、`status = 'paid'` 和金额求和。这里采用示例库的状态编码。
- “按商品分类统计订单数”在有 `orders(id)` 主键和 `order_items(order_id, category)` 的数据源检查联表键、分类分组和订单去重。验收库中同一分类的重复商品明细只贡献一笔订单。

支持范围内，工作区会在展示前核对 SQL。无法确认口径时会请用户核对查询条件，候选行不会作为答案展示。检查只覆盖上述问题和受支持的 SQL 写法，其他数据结构与问法继续沿用现有流程。离线用例用独立 SQLite 库和人工核对的参考查询计算预期值，再用脚本模型验证工作区结果。

### 按数据源配置已付款订单总金额

在当前数据源的“数据库介绍 → 添加知识”点击“填入指标口径模板”。保持标题为
“指标口径：已付款订单总金额”、格式为 JSON。填写订单表、金额字段、年份字段、
付款状态字段和已付款值。年份字段应存四位年份。状态值为文本时使用 JSON 字符串，
为整数时使用 JSON 数字。每个数据源只保留一份配置。

例如，两套结构分别使用以下配置：

```json
{"table":"orders","amount_column":"amount","year_column":"year","status_column":"status","paid_value":"paid"}
```

```json
{"table":"sales","amount_column":"gross","year_column":"fiscal_year","status_column":"payment_code","paid_value":1}
```

分别问“统计2024年已付款订单总金额”。离线验收库的预期分别为 300 和 2300。
第二个库尚未配置时，应提示先配置，随后再问应返回 2300。改问
“统计2023年已付款订单总金额”应返回 1700。把第二个库的年份字段填成
不存在的 `year` 应在保存时提示字段不存在。

这个固定问法直接按当前数据源的配置构造并执行预检过的只读 SQL。
这一版的配置限于单表、独立年份字段和一个已付款状态值。
